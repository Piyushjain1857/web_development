Prompt Engineering

Prompt structure optimization — the difference between "AI gave a weird answer" and "AI did exactly what I needed."

🧩 The 5-part structure that actually works

Stop typing prompts like search queries. Every reliable prompt has these five slots — skip one and the model guesses, and guessing is where bad answers come from:

  • ROLE — who is the model pretending to be? ("You are a senior React reviewer")
  • CONTEXT — what does it need to know that it can't guess? (the actual details, the actual data)
  • TASK — one specific instruction, not three vague ones
  • FORMAT — exact output shape (a list, a table, a word limit, plain text)
  • CONSTRAINTS — what to avoid, edge cases, tone
BEFORE — vague
"write feedback for this student's github profile"
AFTER — structured
ROLE: You're a technical mentor reviewing bootcamp student activity. CONTEXT: 14 commits, 3 repos, 1 pull request, 5-day streak. TASK: Write 2 lines of feedback — 1 strength, 1 area to improve. FORMAT: Two short sentences, no headings. CONSTRAINT: No generic praise. Mention the actual numbers.
REAL USE CASE

Think of a student GitHub leaderboard. "AFTER" is the difference between the AI saying "Great job, keep it up!" for every single student versus saying something that actually reflects that student's numbers — which is the only version worth showing anyone.

⚙️ 4 techniques you'll reach for constantly

Few-shot (show, don't tell)

Give 2-3 example inputs and outputs before asking for the real one. Models copy a pattern far more reliably than they follow an abstract rule.

Delimiters

Wrap raw data in quotes or brackets so the model never confuses "content to process" with "instructions to follow." Example: Summarize the text between the << >> marks.

chain of thought (Step-by-step reasoning)

Adding "think through this step by step before answering" helps on logic-heavy tasks. Skip it for simple tasks — it just makes the answer longer for no benefit.

Lock the format

Say exactly what you want back: "Reply with only the rewritten sentence — no explanation, no extra text." Otherwise you get a polite paragraph wrapped around the actual answer.

COMMON MISTAKE
Asking for "a summary" with no length or format specified — every response comes back a different length and shape, which is fine for a chat but breaks anything that has to display the output consistently.
TRY THIS — 5 MIN, IN CLASS
Pick a prompt someone in the room has actually typed before ("write a project description" or similar). Rewrite it live using ROLE/CONTEXT/TASK/FORMAT/CONSTRAINT on the whiteboard. Run both in any AI chat, 3 times each. The vague one changes every run; the structured one barely moves.
02

AI Response Handling

Streaming responses & formatting — how a real chat app avoids the "stare at a spinner for 8 seconds" problem.

ANALOGY
Non-streamed AI is a waiter who disappears into the kitchen and comes back 8 seconds later with your entire meal at once. Streaming is the same waiter bringing each dish out the moment it's ready — same total time, but you're never left wondering if the kitchen forgot about you. That's exactly why ChatGPT "types" its answer instead of dumping the whole thing at once.

⚡ Why streaming matters

A long AI answer generated all at once can take 5–15 seconds before the user sees anything. Streamed, the first words appear almost instantly and the rest fills in as it's generated. Total time is identical — perceived wait drops to nearly zero. This one decision is the biggest UX lever in any AI feature, more impactful than almost anything else you'll tune.

🧱 Why "formatting" the response is its own skill

Treat AI output as unpredictable text until proven otherwise. Ask an AI for a clean list of items and here's what actually tends to come back:

WHAT YOU ASKED FOR
A plain list of 3 skills, nothing else.
WHAT YOU OFTEN GET
Sure! Here are three skills: 1. Communication 2. Problem-solving 3. Teamwork Let me know if you'd like more!
WHY IT MATTERS
If your app expects only the list to display in a UI, that friendly "Sure! Here are..." intro and the "Let me know..." sign-off are junk it now has to strip out. This is why every real AI feature includes an instruction like "reply with only the list, no greeting, no closing remark" — and still needs a fallback plan for when the model ignores it anyway.

🎯 The 3 formatting problems you'll always run into

  • Extra chatter — greetings, sign-offs, "here's your answer" wrappers around the actual content
  • Inconsistent shape — sometimes a numbered list, sometimes bullets, sometimes a paragraph, for the exact same instruction
  • Partial output mid-stream — while a response is still streaming in, it's temporarily incomplete — you don't try to "read" it as a finished answer until it's fully done arriving
TRY THIS — 5 MIN, IN CLASS
Ask any AI chat for "3 tips for better sleep" twice, in two separate conversations. Compare the shape of both answers side by side — length, whether it uses a list or paragraph, whether it adds a greeting. That inconsistency is exactly what an app has to plan around.

AI Content Generation

Text generation workflows — turning "ask the AI once" into a repeatable process that still works on attempt #200.

🔁 The workflow every content-gen feature follows

User Input
→
Prompt Template
→
AI Generates
→
Clean the Output
→
Show / Save

The key idea: the prompt template is a fixed, reusable pattern — the same skeleton with different details dropped in each time. That's what makes it a "workflow" instead of "typing a new prompt every single time by hand."

THE TEMPLATE (fixed pattern)
Rewrite this raw experience as one ATS-friendly resume bullet, using an action verb and a metric. Target role: [ROLE]. Raw experience: [EXPERIENCE].
FILLED IN FOR ONE STUDENT
Target role: Frontend Developer. Raw experience: "made a small react app that shows weather". → Result: "Built a React weather app integrating a live API to display real-time forecasts."
REAL USE CASE

This exact pattern is what an ATS resume checker feature is doing under the hood — same template, different raw experience dropped in for every user, every bullet point.

📦 When it's not just one person — it's 200 of them

Generating content for one student is easy. Generating it for a whole class on a leaderboard is where the real decisions show up:

  • Don't fire everything at once — send requests in small batches (say, 5 at a time), not all 200 simultaneously, or the service will start rejecting requests for going too fast
  • Plan for some to fail — one student's data being missing or odd shouldn't stop the other 199 from generating
  • Don't regenerate what's already done — save each result against that student's ID so re-running the batch doesn't redo (and re-pay for) everyone from scratch
  • Keep the template short — a long, wordy prompt repeated 200 times adds up in both time and cost far more than people expect
ANALOGY
It's the difference between a single cashier serving customers one at a time versus a checkout line with 5 counters open — the 5-counters version is the "small batches" approach: still controlled, still fair, just not everyone crammed through one register at once.
COMMON MISTAKE
Treating "generate for 1 student" and "generate for 200 students" as the same problem. The moment volume goes up, batching, failure-handling, and cost per request stop being optional details and become the actual design of the feature.
TRY THIS — 5 MIN, IN CLASS
Take the resume bullet template above. As a group, fill it in for 3 different "raw experiences" students call out. Notice the template never changes — only what gets dropped into it does. That's the entire idea of a content-generation workflow.
